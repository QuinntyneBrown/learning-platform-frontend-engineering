Integration and E2E

What belongs at each level, how to make races and retries deterministic, and why the end-to-end suite runs with zero retries.

The thesis

Test behaviour at the cheapest level that can see it.

Own time and order, so every test gives the same answer on every run.

A race depends on two things: time and order. The spec takes control of both. (The pipeline itself: lesson 03.)

Own time. Own order.

Fake timers own time

The debounce fires only when the test advances the clock. No sleeping.

HttpTestingController owns order

Every request waits until the test flushes it, in whatever order the test chooses.

Assert what the user and the network see

apps/web/src/app/features/catalog/catalog.store.spec.ts · condensed
it('drops the slow response for an older query when a newer query is issued', () => {
  store.search('react');
  vi.advanceTimersByTime(250);
  const stale = http.expectOne((r) => r.params.get('q') === 'react');
  store.search('angular');
  vi.advanceTimersByTime(250);
  const fresh = http.expectOne((r) => r.params.get('q') === 'angular');
  // switchMap unsubscribed from the old request, which cancels it: it can never land.
  expect(stale.cancelled).toBe(true);
  fresh.flush(page('Angular Signals in Practice'));
  expect(store.query()).toBe('angular');
  expect(store.items().map((c) => c.title)).toEqual(['Angular Signals in Practice']);
});

What TypeScript can't see

TypeScript: what the code claims

  • A row cast with as: compiles
  • A field JSON.stringify drops: compiles
  • null where a string is promised: compiles

The contract test: the real bytes

  • Documented status, content type, body
  • No extra properties (additionalProperties: false)
  • Every documented response exercised

axe, with a threshold

apps/web/e2e/support.ts · excerpt
/** Fails on serious or critical WCAG 2.2 AA violations; minor ones don't block. */
export async function expectNoSeriousA11yViolations(page: Page): Promise<void> {
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();
  const blocking = results.violations
    .filter((v) => v.impact === 'serious' || v.impact === 'critical')
    .map((v) => `${v.id}: ${v.help} (${v.nodes.map((n) => n.target.join(' ')).join(', ')})`);
  expect(blocking).toEqual([]);
}

One run in twenty: the process

Keeping E2E under ten minutes

  • Only critical journeys at the top; edge cases down the pyramid
  • Set up state through the API, not the UI
  • Data per worker (a tenant each), then run in parallel
  • Shard across CI machines
  • Affected journeys per pull request; everything nightly

A saved sign-in meets rotation

With rotation, a saved refresh cookie works exactly once. Sign in through the API per test, or per worker and user.

Enrolment: each fact tested once

LevelOwnsIn Coursewright
Unit (web)Client policy: one request per double-click; retry a 503 with the same key; new intent, new key; 409 = enrolledenrollment-controller.spec.ts
IntegrationServer truth: 201, replay, 422, 409, 400, cross-tenant 404, against a real database; every shapeenrollments.test.ts, contract.test.ts
E2EOne journey: a real double-click, exactly one POST with a key, "You're enrolled"learner-journey.spec.ts

What production would add

  • A tenant per worker, then fullyParallel and more workers
  • Sharded Playwright across CI machines
  • failOnFlakyTests, so a flake fails the run even with retries (check your version)
  • Component tests and visual regression in Storybook
  • Test data builders instead of hand-written objects
  • Mutation testing on core logic, such as the auth store

Traps

  • Sleeping in tests
  • Letting real timers and networks decide the order of a race
  • Asserting implementation instead of what the user and network see
  • Mocking the thing under test
  • Retries in the E2E configuration
  • Querying by CSS class or test id when a role and name would do
  • One E2E test per edge case

Five questions

Question 1 of 5

What goes in a unit test, an integration test and an end-to-end test for the enroll feature?

Answer out loud.

Model answer
  • Unit: a double-click sends one request
  • Unit: 503 → retry, same key; new intent, new key; 409 = enrolled
  • Integration: 201, replay, 422, 409, 400, 404, real database
  • The contract test on every shape
  • E2E: one real double-click → exactly one POST
Question 2 of 5

How do you test a race condition deterministically?

Answer out loud.

Model answer
  • Control time and order
  • Fake timers own the clock
  • HttpTestingController holds requests; flush in any order
  • Old query, new query: stale cancelled, flush the fresh one
  • No network, no sleep; behaviour, not operators
Question 3 of 5

An E2E test fails one run in twenty. What's your process?

Answer out loud.

Model answer
  • A bug, not noise
  • Reproduce in a loop, tracing on
  • Classify: the test, the app, or the environment
  • Fix the cause; retries stay at zero
  • Quarantine only with an owner and a date
Question 4 of 5

How do you keep an E2E suite under ten minutes as the product grows?

Answer out loud.

Model answer
  • Critical journeys only; edge cases lower down
  • Set up data through the API
  • Data per worker → parallel → sharded
  • Affected journeys per PR, everything nightly
  • Rotating cookies: sign in per test, not one saved state
Question 5 of 5

What does the contract test catch that TypeScript can't?

Answer out loud.

Model answer
  • TypeScript checks claims at compile time
  • The contract test checks the real responses
  • Status, content type and body against openapi.yaml
  • Casts, dropped fields, nulls, undocumented statuses
  • Fails if a documented response is never exercised
