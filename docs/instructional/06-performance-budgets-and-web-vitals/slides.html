The thesis

Measure what users feel, in the field, and make regressions fail the build.

Performance that isn't budgeted erodes, like architecture that isn't linted.

Lab or field?

Lighthouse (lab)

Real-user monitoring (field)

Mid-range phones, forty tabs, real interactions. The number your users feel.

web-vitals, imported lazily

apps/web/src/app/core/observability/rum.ts · excerpt
// Loaded lazily: monitoring code shouldn't compete with the page for the initial bundle.
private async observeWebVitals(): Promise<void> {
  const { onCLS, onINP, onLCP } = await import('web-vitals');
  const report = ({ name, value, rating }: Metric) =>
    this.record({ kind: 'web-vital', name, value, rating, url: this.url() });
  onLCP(report);
  onINP(report);
  onCLS(report);
}

Flush when the page is hidden

apps/web/src/app/core/observability/rum.ts · excerpt
start(): void {
  if (!this.enabled) return;
  void this.observeWebVitals();
  // "hidden" is the last event a page reliably gets: mobile browsers may discard a background
  // tab without ever firing unload. web-vitals reports its final LCP/INP/CLS values then, too.
  this.document.addEventListener('visibilitychange', () => {
    if (this.document.visibilityState === 'hidden') this.flush();
  });
}

Also flushed when a batch reaches MAX_BATCH (10). The beacon and the endpoint are lesson 11.

Lazy route or deferred block?

Lazy route

  • Splits by URL
  • A page: its own guard and title
  • Loaded on navigation

@defer

  • Splits inside a page
  • viewport · interaction · hover · idle · timer · when
  • A chart, an editor, a side panel

Never defer above the fold: it delays LCP and shifts the page.

The core question

INP is poor on the catalog page for low-end Android devices. How do you find the cause?

1Confirm and segment in the field
2Reproduce in a trace
3Read the phase
4Fix by phase, verify in the field

1 · Add attribution and a device class

Sketch · not in this repo · field names from web-vitals 6; check yours
import { onINP } from 'web-vitals/attribution';

onINP(({ name, value, rating, attribution }) => {
  this.record({
    kind: 'web-vital', name, value, rating, url: this.url(),
    target: attribution.interactionTarget,         // which element
    inputDelay: attribution.inputDelay,             // the three phases
    processing: attribution.processingDuration,
    presentation: attribution.presentationDelay,
    cores: navigator.hardwareConcurrency,           // a coarse device class
  });
});

  • Read the interaction's phases in the trace

What one keystroke does

protected onSearch(value: string): void {
  this.query.set(value);
  // replaceUrl: one history entry for the page, not one per keystroke.
  void this.router.navigate([], {
    relativeTo: this.route,
    queryParams: { q: value || null },
    replaceUrl: true,
  });
}

Cheap on a laptop. Measure it on a phone before you decide.

What production would add

  • Server rendering with incremental hydration for public catalog pages
  • Optimized, responsive images
  • Lighthouse checks in CI on key pages
  • Attribution and device class in the RUM data

Traps

  • Measuring only with Lighthouse on a fast laptop
  • Raising the budget every time it fails
  • Re-exporting something heavy from a barrel
  • Deferring content above the fold
  • Tracking list items by index
  • OFFSET pagination behind an infinite scroll
  • Ten thousand rows in the DOM
  • Loading monitoring or third-party scripts eagerly
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

INP is poor on the catalog page for low-end Android devices. How do you find the cause?

Answer out loud.

Model answer
  • Field first: p75 INP for the route, by device class
  • Attribution: which element, which phase
  • Reproduce in a throttled trace or on a real phone
  • Input delay → long tasks · processing → handler · presentation → DOM
  • Confirm the fix in field data
Question 2 of 5

What goes in the initial bundle, and how do you keep it there?

Answer out loud.

Model answer
  • Framework, shell, auth, HttpClient, the shell's primitives
  • Lazy routes; @defer below the fold
  • Heavy dependencies behind their own entry point
  • Monitoring imported lazily
  • A budget that fails CI: 350 kB warn, 500 kB fail; today ~333 kB
Question 3 of 5

When would you use a deferred block, and when a lazy route?

Answer out loud.

Model answer
  • Lazy route: splits by URL; a page with its guard and title
  • @defer: splits inside a page, on a trigger
  • Placeholder and loading states; prefetch
  • Coursewright defers the enrollments panel
  • Never above the fold
Question 4 of 5

Why is OFFSET 10000 slow, and what does a keyset cursor need from the index?

Answer out loud.

Model answer
  • OFFSET reads and discards every skipped row
  • Inserts shift pages: duplicates and gaps
  • Keyset seeks past the last row's sort key
  • Index: equality filter, sort columns, unique tiebreaker
  • (tenant_id, title, id); a test walks every page
Question 5 of 5

How would you render a list of 10,000 rows?

Answer out loud.

Model answer
  • Page on the server with a keyset cursor
  • If truly needed: virtualize (CDK viewport)
  • Costs: heights, find in page, screen readers
  • Track by ID; heavy work on the server
  • content-visibility as a middle ground
