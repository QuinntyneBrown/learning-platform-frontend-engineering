Coursewright frontend · Lesson 01

Layers, Boundaries and
the Design System

How a large Angular app stays changeable: one-way layers, rules the build enforces, and primitives that keep the browser's behaviour.

The questions this lesson answers

  • How do you structure a large Angular app so it stays maintainable?
  • Why is the button an attribute selector, not an element?
  • Two features need the same course card: where does it go?
  • How do tokens support per-tenant branding without a build per tenant?
  • How do you roll out a breaking change used in 200 places?
The thesis

Architecture that isn't executable erodes.

The right thing is the easy thing. The wrong thing fails the build.

Large frontends fail by erosion

  • A feature imports a helper from another feature's folder
  • The design system injects an application service
  • Each change is reasonable, and passes review
  • A year later, nothing moves without breaking something else

The rules, in the lint config

apps/web/eslint.config.js
// Architectural boundaries, enforced by lint rather than by convention:
//   design-system  -> depends on nothing in the app
//   core           -> may use design-system; never features or shell
//   features/<x>   -> may use core and design-system; never another feature
//   shell          -> may use core and design-system

const restrict = (regex, message) => ({
  'no-restricted-imports': ['error', { patterns: [{ regex, message }] }],
});

One rule per feature, generated

apps/web/eslint.config.js
const features = featureNames();
// …
...features.map((feature) => ({
  files: [`src/app/features/${feature}/**/*.ts`],
  rules: restrict(
    `(^|/)(${[...features.filter((f) => f !== feature), 'shell'].join('|')})/`,
    'A feature must not import another feature or the shell. Move shared code to core or the design system.',
  ),
})),

featureNames() reads the features folder when lint runs, so a sixth feature is covered automatically.

Errors that teach

pnpm lint, after adding an import of ../catalog/catalog.store to features/course/course-page.ts

error '../catalog/catalog.store' import is restricted from being used by a pattern. A feature must not import another feature or the shell. Move shared code to core or the design system no-restricted-imports

The architecture is explained at the moment someone needs it, not by a reviewer for the fifth time.

Be honest about the limits

What lint can't do

  • Checks import paths, not a dependency graph
  • A creative relative path can dodge it
  • No project graph: CI runs everything

When to revisit (Nx or libraries)

  • More than one app
  • CI time dominated by work a change didn't touch

Tokens: CSS custom properties

apps/web/src/app/design-system/tokens.css · excerpt
/*
 * Design tokens. Components read only these custom properties, so a theme (or a tenant's
 * brand) is a matter of redefining them. Every text/background pair meets WCAG AA (4.5:1);
 * borders of form controls and the focus ring meet the 3:1 non-text contrast minimum.
 */
:root {
  --cw-color-bg: #ffffff;
  --cw-color-text: #1b1f24;
  --cw-color-primary: #1d4ed8;
  --cw-space-4: 1rem;
  --cw-radius-md: 0.5rem;
  --cw-focus-ring: 3px solid var(--cw-color-focus);
}

Dark mode: same properties, new values

A tenant's brand is data

Sketch · not in this repo · applied after sign-in
const root = document.documentElement;
for (const [token, value] of Object.entries(tenant.brandTokens)) {
  root.style.setProperty(token, value);   // e.g. '--cw-color-primary', '#0f766e'
}

Not this

A build per tenant. Components branching on tenant IDs.

This

Redefine the same custom properties. The components don't change.

The catch: contrast

4.5 : 1

Every text and background pair (WCAG AA)

3 : 1

Control borders and the focus ring (non-text contrast)

Validate brands when they're configured: the tenant picks a brand color, the platform derives the text color on it, or rejects it.

The button is an attribute component

apps/web/src/app/design-system/button/button.ts · excerpt
@Component({
  selector: 'button[cwButton], a[cwButton]',
  template: '<ng-content />',
  // …
  host: {
    class: 'cw-button',
    '[class.cw-button--secondary]': "variant() === 'secondary'",
    '[attr.aria-busy]': 'busy() || null',
  },
})
export class Button {
  readonly variant = input<ButtonVariant>('primary');
  readonly busy = input(false);
}

Used as <button cwButton type="button" [busy]="…">Enroll</button>

Why an attribute, not an element?

button[cwButton]

Keeps focus, Enter and Space, form submission, the button role, its accessible name, disabled.

<cw-button> → div

Loses all of it. A sprint of key handlers and ARIA, and still a missed case.

<cw-button> → button

Must forward type, form and every ARIA attribute. The API grows forever.

Busy, not disabled

apps/web/src/app/design-system/button/button.ts
/**
 * An attribute component on the native element, …
 *
 * `busy` sets aria-busy instead of `disabled`: a disabled button drops focus and swallows
 * clicks, which would hide double-submits from the code designed to absorb them (exhaustMap).
 */

disabled

Drops focus, hides why, swallows clicks

aria-busy

Focus stays; a spinner shows; the logic (lesson 03) absorbs duplicates

The text field owns the wiring

apps/web/src/app/design-system/text-field/text-field.html · excerpt
<label class="label" [for]="inputId">{{ label() }}</label>
@if (hint()) {
  <p class="hint" [id]="hintId">{{ hint() }}</p>
}
<input
  [id]="inputId"
  …
  [attr.aria-describedby]="describedBy()"
  [attr.aria-invalid]="error() ? 'true' : null"
  …
/>
@if (error()) {
  <p class="error" [id]="errorId">{{ error() }}</p>
}

A ControlValueAccessor, so it works with any Angular form. The error has no role="alert": the form's summary announces.

Three scenarios that come up again and again

1Two features need the same course card
2A team wants to add a date picker
3A breaking change used in 200 places

1 · The same course card in two features

Import it from catalog

Couples two features' releases and ownership. Lint blocks it anyway.

Split generic from specific

A card with plain inputs moves into the design system. Each feature maps its own data onto it.

Shared behaviour, like loading a course, moves into core.

2 · Before accepting a date picker

  • A ControlValueAccessor: works with any Angular form
  • Labelled, with hint and error wiring
  • Fully keyboard-usable (ARIA pattern), or the native date input
  • Explicit about time zones
  • Reads only tokens
  • Tests, including an automated accessibility check

3 · A breaking change used in 200 places

1New API alongside the old
2Deprecate + lint warning
3Codemod (Angular schematic)
4Migrate in reviewable batches
5Visual regression tests
6Remove in the next major

Strangler thinking, at component scale.

What production would add

  • A published component library (ng-packagr)
  • Storybook, with interaction and accessibility tests per component
  • Visual regression tests
  • A written deprecation policy

Traps

  • A div in a component, called a button
  • Hard-coded colors inside components
  • A feature importing another feature "just this once"
  • A design system that depends on the app
  • Barrels treated as free
  • Lint rules mistaken for a dependency graph
  • role="alert" on every field error
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you structure a large Angular application so it stays maintainable?

Answer out loud.

Model answer
  • One-way layers: design system → core → shell and features
  • Features never import each other; shared code moves down
  • A public surface per layer (path alias + barrel)
  • Executable: lint rules per feature; CI fails on a violation
  • Nx tags once there's more than one app
Question 2 of 5

Why is the design system's button an attribute selector, not an element?

Answer out loud.

Model answer
  • The native button gives focus, keys, submission, role, name, disabled
  • An attribute component keeps all of it and adds styling
  • A div wrapper loses it; a button wrapper forwards attributes forever
  • Busy is aria-busy, so double clicks reach the logic
Question 3 of 5

Two features need the same course card. Where does it go?

Answer out loud.

Model answer
  • Never imported from one feature into another
  • Presentational part → design system, with plain inputs
  • Each feature maps its own data onto it
  • Shared behaviour → core
Question 4 of 5

How do design tokens support per-tenant branding without a build per tenant?

Answer out loud.

Model answer
  • Components read only CSS custom properties
  • A theme is data: redefine them; no re-render, no rebuild
  • Dark mode already works this way; tenant brands the same
  • Validate contrast at configuration time
Question 5 of 5

How would you roll out a breaking change to a design-system component used in 200 places?

Answer out loud.

Model answer
  • New API alongside the old; deprecate the old
  • Lint warning for new uses; a codemod for the rest
  • Reviewable batches, visual regression tests
  • Remove in the next major, at zero warnings
