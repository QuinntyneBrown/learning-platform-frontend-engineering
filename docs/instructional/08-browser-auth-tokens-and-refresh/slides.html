Browser Auth:
Tokens and Refresh

Where tokens live, how they rotate, how one refresh serves five 401s, and why the server, not a guard, decides.

The questions this lesson answers

  • Where would you store tokens in a SPA, and why not localStorage?
  • Walk through OIDC authorization code + PKCE. What does PKCE protect against?
  • What does SameSite=Strict stop, and what doesn't it stop?
  • Two tabs refresh at once with rotation on. What happens?
  • How do you test that a learner can't export reports?
The thesis

The browser is hostile territory.

Give script as little as possible. Give every credential a short life. Enforce every rule on the server.

Two attackers

No storage is safe from both

Where the credential livesXSS (script on your page)CSRF (another site)
localStorageReads it, sends it anywhere, keeps itNot exposed
Memory (a signal)Uses it while the page is openNot exposed
HttpOnly cookieCan't read itSent automatically, unless SameSite stops it

Decide where each credential lives by what it's worth.

ADR-0003: four options

1 · Both in localStorage

Simple, survives reloads. Any script can read both.

2 · Memory + HttpOnly cookie

Chosen. Script can't read the refresh token.

3 · Token handler

Session cookie only. The BFF holds every token.

4 · OIDC + PKCE

Straight against an identity provider.

The access token: a signal, nothing else

apps/web/src/app/core/auth/auth.store.ts · excerpt
// In memory only, never localStorage or sessionStorage: any script on the page can read
// storage, so a single XSS bug would leak the token. After a reload, restore() gets a new
// access token from the httpOnly refresh cookie, which script can't read at all.
private readonly session = signal<Session | null>(null);
private refreshInFlight: Observable<Session> | null = null;

readonly user = computed(() => this.session()?.user ?? null);
readonly accessToken = computed(() => this.session()?.accessToken ?? null);
readonly isAuthenticated = computed(() => this.session() !== null);

Access token

JWT · 15 minutes · in the login response body

Refresh token

Opaque, random · 7 days · HttpOnly cookie

Be precise about what that buys

XSS can still

  • Call the API with the in-memory token
  • Call /api/auth/refresh and read the new access token

XSS can't

  • Read the refresh cookie
  • Walk away with a credential that works for a week

The real defence against XSS is not having it: Angular's sanitization and a strict CSP.

Each refresh token works exactly once

/** Spends a refresh token and issues its replacement. Each token works exactly once. */
export function rotateRefreshToken(
  db: DatabaseSync,
  presented: string,
  now = Date.now(),
): Rotation {
  // …
  if (row.expires_at <= now) return { ok: false, reason: 'expired' };

  return transaction(db, () => {
    revokeRefreshToken(db, presented, now);
    return { ok: true, userId: row.user_id, token: issueRefreshToken(db, row.user_id, now) };
  });
}

Reuse detection

apps/bff/src/auth/refresh-tokens.ts
if (row.revoked_at !== null) {
  // Reuse detection: a spent token coming back means two parties hold it, and we can't tell
  // which one is the thief. Revoke every token the user has, so both must sign in again.
  // (Two tabs refreshing with the same cookie at once would also land here; the web app
  // single-flights its refresh, and some systems allow a few seconds' grace instead.)
  db.prepare(
    'UPDATE refresh_tokens SET revoked_at = ? WHERE user_id = ? AND revoked_at IS NULL',
  ).run(now, row.user_id);
  return { ok: false, reason: 'reused' };
}

Refresh once, retry once

apps/web/src/app/core/auth/auth.interceptor.ts · condensed
return next(withToken(request, auth.accessToken())).pipe(
  catchError((error: unknown) => {
    if (!(error instanceof HttpErrorResponse) || error.status !== 401) {
      return throwError(() => error);
    }
    // The access token expired: refresh once, then retry once. A second 401 propagates.
    return auth.refresh().pipe(
      catchError(() => {
        // The refresh cookie is gone or revoked too. AuthStore has already cleared the session.
        // … navigate to /login with a returnUrl …
        return throwError(() => error);
      }),
      switchMap((session) => next(withToken(request, session.accessToken))),
    );

The retry sits outside both error handlers: a second 401 reaches the caller. No loop.

Four behaviours, four tests

  • sends the bearer token, but not to auth endpoints
  • refreshes once and retries once after a 401
  • shares one refresh between concurrent 401s
  • signs out and sends the user to the login page when the refresh fails

Five parallel 401s

One in-flight refresh, shared

apps/web/src/app/core/auth/auth.store.ts
/**
 * Concurrent callers share one request. Refresh tokens are single-use, so a second parallel
 * refresh would present a spent token, and the BFF's reuse detection would revoke the session.
 */
refresh(): Observable<Session> {
  this.refreshInFlight ??= this.api.refresh().pipe(
    tap({
      next: (session) => this.session.set(session),
      error: () => this.session.set(null),
    }),
    finalize(() => (this.refreshInFlight = null)),
    share(),
  );
  return this.refreshInFlight;
}

/**
 * A route-level onRequest hook. It runs after authentication but before body validation,
 * so a caller without the role can't probe the request schema.
 */
export function requireRole(role: Role) {
  return async (request: FastifyRequest, reply: FastifyReply) => {
    if (!request.user.roles.includes(role)) {
      return sendProblem(reply, { status: 403, detail: `This needs the ${role} role.` });
    }
  };
}

Who gets the cookie sent?

Illustrative domains. A same-site call to refresh returns the token in the body, which a cross-origin page can't read.

What SameSite=Strict doesn't stop

Stops

  • A hostile page forcing a refresh or a logout
  • Any request another site starts

Doesn't stop

  • XSS: it runs on your own site
  • A compromised sibling subdomain
  • A cookie that's already stolen

Bearer-token calls need no CSRF defence: the browser never adds an Authorization header by itself.

Strict's usual cost

The cost

A link from an email arrives without the cookie.

Not here

Only the app's own fetch calls use the cookie, after the page loads.

Set it explicitly

As of September 2026, browsers still differ when it's missing.

Two tabs, one cookie jar

Three fixes

Web Locks

Serialize refreshes across tabs. The second tab waits, then sends the new cookie.

BroadcastChannel

One tab refreshes and shares the access token with the others.

Grace window

The server accepts a just-spent token for a few seconds. Widens the thief's window.

ADR-0003: "A BroadcastChannel or a tab lock would coordinate them; this repo doesn't."

A tab lock around the refresh

Sketch · not in this repo · auth.store.ts
refresh(): Observable<Session> {
  this.refreshInFlight ??= defer(() =>
    // One refresh at a time across every tab of this origin.
    navigator.locks.request('cw-refresh', () => firstValueFrom(this.api.refresh())),
  ).pipe(/* tap, finalize and share, as today */);
  return this.refreshInFlight;
}

The browser reads the cookie when the request is sent, so the waiting tab sends R2, not R1.

ADR-0003

In production, sign-in would be OIDC + PKCE, with the BFF as the confidential client, and the rest of this design stays the same.

Authorization code + PKCE

What PKCE protects against

Code interception

A code stolen from a redirect, a log or the history is useless without the verifier, which never left the client.

As of September 2026

OAuth security guidance: PKCE for every client, confidential ones included. The implicit flow, tokens in the URL, is deprecated.

What production would add

  • A real identity provider: OIDC + PKCE
  • SAML single sign-on for enterprise tenants
  • Possibly the token handler pattern, with CSRF tokens
  • Multi-factor authentication and audit logs
  • Cross-tab coordination (Web Locks or BroadcastChannel)
  • A strict content security policy

Traps

  • Tokens in localStorage, because it's convenient
  • "HttpOnly makes us safe from XSS"
  • One refresh per 401, with rotation on
  • A retry without a limit
  • A hidden link or a route guard treated as authorization
  • The tenant read from a header or the URL; 403 across tenants
  • Forgetting a JWT still works after logout, until it expires
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

Where would you store tokens in a single-page app, and why not localStorage?

Answer out loud.

Model answer
  • What script can read, XSS can steal; localStorage persists
  • Access token: 15 minutes, in memory, in a signal
  • Refresh token: HttpOnly, SameSite=Strict, /api/auth, rotating
  • A reload restores the session with a silent refresh
  • Stronger still: a token handler, session cookie only
Question 2 of 5

Walk through OIDC authorization code with PKCE. What does PKCE protect against?

Answer out loud.

Model answer
  • Random verifier; send only its hash (challenge) + state
  • User signs in at the identity provider
  • One-time code comes back; check the state
  • Exchange code + verifier; provider checks the challenge
  • Stops code interception; run it from the BFF
Question 3 of 5

What does SameSite=Strict stop, and what doesn't it stop?

Answer out loud.

Model answer
  • Stops: the cookie on requests another site starts
  • Doesn't stop XSS on your own site
  • Doesn't stop a compromised sibling subdomain
  • Does nothing for a cookie already stolen
  • Cost: email links arrive without it (not here)
Question 4 of 5

Two tabs refresh at the same moment with rotation on. What happens, and how would you fix it?

Answer out loud.

Model answer
  • Tabs don't share memory, but do share the cookie jar
  • Same token sent twice: one rotates, one looks reused
  • Every session revoked; a false alarm logged
  • Fix: Web Locks, or one tab + BroadcastChannel
  • Or a short server grace window, slightly less secure
Question 5 of 5

How do you test that a learner can't export reports?

Answer out loud.

Model answer
  • At the server: that's where the rule lives
  • Real login as a learner → POST /api/reports → 403
  • Someone else's job → 404, also tested
  • The E2E hidden-link check is UX only
  • At scale: every role × every protected route
