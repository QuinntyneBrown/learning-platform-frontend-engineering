The thesis

Accept fast. Work in the background. Push progress, poll as the fallback.

And make every step safe to repeat.

ADR-0005: why a job, not a long request

Must not

  • Lose the work to a 60-second proxy timeout
  • Lose it, or start it twice, when the user navigates away

Must

  • Show live progress
  • Say when a retry happens

The queue is a seam

export interface Delivery<T> {

/**
 * The seam between "accept the work" and "do the work". Swap InMemoryJobQueue for SQS (a

 * table plus a relay, and the routes and the worker don't change.
 */
export interface JobQueue<T> {
  publish(message: T): Promise<void>;
  subscribe(handler: MessageHandler<T>): void;
}

Backoff, then the dead-letter list

apps/bff/src/jobs/queue.ts · InMemoryJobQueue
async #deliver(message: T, attempt: number): Promise<void> {
  try {
    if (!this.#handler) throw new Error('The queue has no subscriber.');
    await this.#handler({ message, attempt });
  } catch {
    if (attempt >= this.#maxAttempts) {
      this.deadLetters.push(message);
    } else {
      this.#schedule(message, attempt + 1, this.#retryBaseMs * 2 ** (attempt - 1));
    }
  }
}

"After maxAttempts failures the message moves to deadLetters for a human to inspect, instead of retrying forever." Defaults: 3 attempts, 500 ms base.

Two comments carry the design

apps/bff/src/routes/reports.ts · excerpt
// Every event is a full snapshot, so a client that reconnects needs no replay: the first
// event brings it up to date, and Last-Event-ID can be ignored.

  response.write(`id: ${sequence}\nevent: job\ndata: ${JSON.stringify(job)}\n\n`);

// A comment line keeps idle proxies and load balancers from timing the connection out.

// …
response.on('close', close); // the client went away

Why SSE?

SSE

One-way. Plain HTTP: it proxies and authenticates like any request. Event ids for resuming.

WebSocket

Two-way, a protocol upgrade of its own. Overkill for progress.

Polling

The simplest of all. Here, the fallback.

SSE over fetch, with the token

What fetch costs you

EventSource gives, fetch doesn't

  • Automatic reconnect
  • Last-Event-ID on the reconnect

Why Coursewright can afford it

  • Every event is a full snapshot
  • Any failure falls back to polling

The fallback is one line

apps/web/src/app/features/reports/job-progress.ts
/** Job snapshots until the job completes or fails: pushed over SSE, or polled as a fallback. */
watchJob(jobId: string): Observable<Job> {
  // Any stream failure (a network drop, a 401 from an expired token, a stream cut off
  // early) falls back to polling. Polling goes through HttpClient, so it gets the
  // interceptors' token refresh and tracing back.
  return this.stream(jobId).pipe(catchError(() => this.poll(jobId)));
}

Polling with backoff

apps/web/src/app/features/reports/job-progress.ts · excerpt
/** 1 s, 2 s, 4 s, then every 8 s. */
export const pollDelay = (poll: number) => Math.min(1000 * 2 ** (poll - 1), 8000);
// …
private poll(jobId: string): Observable<Job> {
  // Each repeat resubscribes to the cold HttpClient observable, which sends a new request.
  return this.api.getJob(jobId).pipe(
    repeat({ delay: (poll) => timer(pollDelay(poll)) }),
    takeWhile((job) => !isTerminal(job), true),
  );
}

One process here, two systems in production

Coursewright

The job store and the queue share one process's memory. They can't disagree.

Production

A database and a queue. No transaction spans both.

The dual write fails both ways

Publish, then commit

The commit fails. A consumer works on a job that doesn't exist.

Commit, then publish

A crash in between. The job is saved but never published.

The costs ADR-0005 admits

One process

Jobs live in memory. A restart loses them.

One instance

Two BFF instances wouldn't share jobs.

A connection per tab

HTTP/1.1: six per origin. HTTP/2 removes the limit.

What production would add

  • Job state in the database
  • SSE fan-out across BFF instances: Redis pub/sub, or a consumer per instance
  • Results in storage, behind presigned URLs
  • Versioned event schemas
  • traceparent in every envelope: browser → queue → worker

The request path

2Upload to storage via a presigned URL
3POST the import with an Idempotency-Key
4Manager role; tenant from the token
5Job + outbox row in one transaction
6202 Accepted with a Location

One idempotency key per intent, reused on retries: lesson 03.

The work path

Batches

A few hundred rows per transaction. The unique constraint makes a redelivered batch harmless.

Bad rows

Don't fail the job. They go into an error report to download, fix and upload again.

Transient failures

Retry with exponential backoff.

Poison messages

To the dead-letter queue. The job is marked failed.

Traps

  • Holding a request open for the whole job
  • 201 for work that hasn't happened yet
  • The token in the query string, so EventSource can connect
  • Forgetting fetch skips the interceptors: no token, no trace
  • Assuming a network chunk is a whole message
  • Streaming deltas instead of snapshots
  • Retrying forever, with no dead-letter queue
  • Publishing before committing, to consumers that aren't idempotent

Five questions

Question 1 of 5

Design bulk-enrolling 5,000 learners from a CSV upload, end to end.

Answer out loud.

Model answer
  • Validate in the browser; upload to storage
  • POST with an Idempotency-Key → 202 + Location
  • Role, tenant from the token; job + outbox in one transaction
  • Batches in transactions; UNIQUE (user, course)
  • Error report for bad rows; DLQ; counts over SSE + polling
Question 2 of 5

The SSE connection drops at 60%. What does the user see, and what does the code do?

Answer out loud.

Model answer
  • Server: 'close' → unsubscribe; the job carries on
  • Browser: the reader fails → catchError → poll
  • Polling uses HttpClient, so an expired token refreshes
  • First poll: the current snapshot; then 1 s → 8 s
  • Gap: a polling error ends it, with no retry
Question 3 of 5

Why is "publish to the queue, then commit to the database" wrong? What's the fix?

Answer out loud.

Model answer
  • No transaction spans a queue and a database
  • Publish, then a failed commit: a phantom job
  • Commit, then a crash: saved, never published
  • Outbox: state + event row in one transaction; a relay publishes
  • The relay may publish twice: idempotent consumers
Question 4 of 5

How do you make a consumer idempotent?

Answer out loud.

Model answer
  • Assume every message arrives more than once
  • Record message ids in the same transaction as the effect
  • Idempotent by design: unique constraints, upserts
  • States that only move forward
  • Side effects, like emails, behind the same check
Question 5 of 5

When would you pick polling over SSE, even with SSE available?

Answer out loud.

Model answer
  • Rare updates, or jobs that take minutes
  • Many watchers: a connection each; six per origin on HTTP/1.1
  • Proxies that buffer or cut streams; serverless backends
  • Simpler, cacheable, easy to scale
  • Coursewright: SSE first, polling with backoff as the fallback
