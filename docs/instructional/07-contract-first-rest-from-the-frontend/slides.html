from the Frontend

One hand-written OpenAPI file, generated types, both sides held to it, and changes made additively.

The thesis

The contract is code: write it first, generate from it, validate against it on both sides, and change it additively.

The conventions, at the top of the file

contracts/openapi.yaml · excerpt
info:
  # …
  description: |
    The backend-for-frontend that the Coursewright web app calls. This file is the
    source of truth: `schema.d.ts` is generated from it, the web app and the BFF both
    import those types, and the BFF's contract tests validate real responses against it.

    Conventions:
    - Errors are RFC 9457 problem details (`application/problem+json`).
    - Every request may carry a W3C `traceparent` header; the BFF continues that trace
      and returns `traceparent` on the response.
    - The tenant comes from the access token, never from the request. A resource that
      belongs to another tenant is a 404, not a 403, so its existence doesn't leak.

One error shape: RFC 9457

apps/bff/src/problem.ts · excerpt
/**
 * Sends an RFC 9457 problem. Without a `type` it is `about:blank`, whose title is the HTTP status
 * text, as the RFC asks.
 */
export function sendProblem(reply: FastifyReply, problem: ProblemInit): FastifyReply {
  const { status, type = 'about:blank', title = STATUS_CODES[status] ?? 'Error', detail } = problem;
  return reply
    .code(status)
    .type('application/problem+json')
    .send({ type, title, status, detail, traceId: reply.request.id });
}

One function turns errors into sentences

apps/web/src/app/core/problem.ts · excerpt
const FALLBACK = 'Something went wrong. Please try again.';

/** A message fit to show a user, from an RFC 9457 problem+json error when the BFF sent one. */
export function problemMessage(error: unknown, fallback = FALLBACK): string {
  if (!(error instanceof HttpErrorResponse)) return fallback;
  if (error.status === 0) return 'Unable to reach the server. Check your connection and try again.';
  return isProblem(error.error) ? (error.error.detail ?? error.error.title) : fallback;
}

A strong ETag from the exact bytes

apps/bff/src/routes/courses.ts · excerpt
// Hash the exact bytes we send, so the ETag changes whenever the body does, `enrolled`
// included. A 304 saves the transfer and the client's parse, not the query.
const body = JSON.stringify(course);
const etag = `"${sha256(body)}"`;
// `private`: the body is per-user, so shared caches must not keep it.
// `no-cache`: the browser may keep it but must revalidate first, which the ETag makes cheap.
reply.header('etag', etag).header('cache-control', 'private, no-cache');

if (matchesIfNoneMatch(request.headers['if-none-match'], etag)) {
  return reply.code(304).send();
}
return reply.type('application/json; charset=utf-8').send(body);

The browser's cache does the revalidation

ETag or max-age?

ETag + no-cache

  • Saves: the bytes
  • Costs: a round trip, and the query
  • Risk: none. Never stale

max-age=N

  • Saves: the whole request, for N seconds
  • Risk: stale data you can't recall
  • Per-user data: private, always

A short max-age plus an ETag suits shared, slow-changing data. Per-user state: revalidate.

/**

Why store a hash of the request?

The key alone

A client bug reuses a key for another course. The server replays the first course's 201. The user thinks they enrolled; they didn't.

Key + request hash

The same key with a different body is caught: a loud 422, idempotency-key-reused.

UNIQUE (user_id, course_id) stays as the last line for separate intents: 409.

Which side moves first?

A response field

Server sends both first. Clients switch. Server drops the old one.

A request field

Server accepts both first: a strict schema would reject the new name with a 400. Clients switch. Server stops accepting the old one.

Two cautions

A new unit is a new field

Minutes to an ISO 8601 duration string isn't a rename. Name the unit.

The BFF can absorb it

A platform service renames its field; the BFF maps it, and the web contract doesn't change.

What production would add

  • oasdiff breaking-change check against main (ADR-0002's production note)
  • Consumer-driven contract tests between teams (Pact)
  • A generated client that types paths and parameters
  • Sampled production responses validated against the schema

Traps

  • Hand-writing a wire type "just this once"
  • Treating http.get<T> as validation
  • Renaming a field in one release: open tabs break
  • 403 for another tenant's resource: it confirms existence
  • A new idempotency key per retry
  • A key without a request hash: silent wrong replays
  • An ETag computed from anything but the bytes sent
  • Error bodies that echo internals instead of a trace ID
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

The backend team wants to rename durationMinutes to duration. How do you roll it out with zero downtime?

Answer out loud.

Model answer
  • Expand: both fields in the contract, old one deprecated
  • BFF sends both; strict schemas force contract-first
  • Migrate the web; types and templates find every use
  • Wait for old tabs and consumers, based on data
  • Then remove. Request fields: server accepts both first
Question 2 of 5

The same Idempotency-Key arrives twice: same body, then a different one. What does the server do, and why store a hash?

Answer out loud.

Model answer
  • Key per user, with a request hash and the saved response
  • Same hash: replay the 201 and body, idempotency-replayed: true
  • Different hash: 422, key reused, never a wrong replay
  • Enrollment + saved response in one transaction
  • Several instances: key row first, in progress; 409 to a duplicate
Question 3 of 5

Where does each status code end up in the UI of a form?

Answer out loud.

Model answer
  • 400: rare; the problem's detail in the one alert
  • 401: the interceptor; wrong password on sign-in
  • 403: a message; don't offer the action
  • 404 changes the page; 409 can be success; 422 is a bug
  • 0 and 5xx: retry with backoff; show the trace ID
Question 4 of 5

What does an ETag save compared with max-age, and what does each risk?

Answer out loud.

Model answer
  • ETag + no-cache: a 304 saves bytes, not the round trip
  • Never stale
  • max-age: no request at all, but stale and unrecallable
  • Per-user: private either way
  • ETags for per-user state; short max-age for shared data
Question 5 of 5

How would you detect contract drift between two teams' services?

Answer out loud.

Model answer
  • One spec; generated types; contracts:check in CI
  • Requests validated against the spec's schemas
  • A contract test on every documented response
  • Between teams: Pact, verified by the provider; oasdiff
  • Production: validate sampled responses, alert
