Events over time: a search that survives a slow response, a button that absorbs double clicks, and a key that makes retries safe.

The thesis

A flattening operator is a concurrency decision. No operator makes a write safe on its own.

The server has to recognize a repeat.

Same job, different rule when B arrives early

Pick the operator for its concurrency rule

OperatorRuleUsed for
switchMapThe newest wins; cancel the previous oneTypeahead search, in the catalog store
exhaustMapIgnore new events while one is in flightEnroll button, "Load more"
concatMapQueue, and run in orderOrdered saves (not needed here)
mergeMapRun all at once, optionally with a concurrency limitPrefetching (not needed here)

"sig", pause, "nals"

switchMap: unsubscribe first, then subscribe

apps/web/src/app/features/catalog/catalog.store.ts · excerpt
// switchMap cancels the stale request, so a slow response for an old query can't
// arrive late and overwrite the results for the newer one.
switchMap((query) =>
  api.searchCourses({ q: query }).pipe(
    tap(({ items, nextCursor }) =>
      patchState(store, { items, nextCursor, status: 'loaded' }),
    ),
    catchError(fail),
  ),
),

Unsubscribing from an HttpClient request aborts it.

The same keystrokes, other operators

mergeMap

Both live. "sig" lands last and overwrites "signals". The classic race.

concatMap

"signals" waits for the slow "sig". Correct, but slow.

exhaustMap

"signals" is ignored. The user never gets what they asked for.

switchMap

The newest wins. The stale answer can't land.

The caveat

Cancelling is client-side. The server may still run the query.

For a read, that's harmless. For a write, it's the whole problem.

Catch inside, not outside

Outer catch

One 503 and the pipeline is gone. Keystrokes still set the signal; nothing listens.

Inner catch

That request ends quietly. The error is in state. The stream carries on.

Load more: exhaustMap

        // …
      );
    }),
  ),

A double click on "Load more"

mergeMap

The same cursor twice. Duplicate courses appended.

concatMap

The second click is queued. Two pages load.

switchMap

Cancel, refetch the same cursor. May never finish.

exhaustMap

The second click is ignored. One page.

Two streams, one state: guard the stale page

apps/web/src/app/features/catalog/catalog.store.ts · excerpt
const query = store.query();
// …
return api.searchCourses({ q: query, cursor: store.nextCursor() ?? undefined }).pipe(
  tap(({ items, nextCursor }) => {
    // A new search may have started meanwhile; this page belongs to the old one.
    if (store.query() !== query) return;
    patchState(store, { items: [...store.items(), ...items], nextCursor });
  }),
  catchError(fail),
  finalize(() => patchState(store, { loadingMore: false })),
);

A new search doesn't cancel an in-flight page: they're separate streams.

Enroll: exhaustMap for a write

apps/web/src/app/features/course/enrollment-controller.ts · condensed
private readonly intents = new Subject<string>();
// …
constructor() {
  this.intents
    .pipe(
      // exhaustMap, not switchMap: a second click must not cancel an in-flight enrollment
      // (the server may already have done the work), nor start a second one. It is ignored.
      exhaustMap((courseId) => this.send(courseId)),
      takeUntilDestroyed(),
    )
    .subscribe();
}

Provided by the course page; clicks call enroll(courseId), which calls intents.next().

What exhaustMap can't see

It sees

  • Overlapping clicks in one stream, in one tab

It can't see

  • A retry after a lost response
  • A second tab
  • A reload, then another click
  • A proxy that retries

Only the server can recognize the same intent twice.

One key per intent

apps/web/src/app/features/course/enrollment-controller.ts · excerpt

  // One key per intent, reused by every retry: if a response is lost and the retry reaches
  // the server, the server recognizes the key and replays the first result instead of
  // enrolling twice.
  const idempotencyKey = crypto.randomUUID();
  this.status.set('pending');
  this.error.set(null);

  return this.api.enroll(courseId, idempotencyKey).pipe(

Retry transient errors, with backoff

apps/web/src/app/features/course/enrollment-controller.ts · excerpt
/** Retry network failures and 5xx only; a 4xx won't change by asking again. */
const isTransient = (error: unknown) =>
  error instanceof HttpErrorResponse && (error.status === 0 || error.status >= 500);

/** 300 ms, then 600 ms. */
export const backoff = (retryCount: number) => 300 * 2 ** (retryCount - 1);
// …
retry({
  count: 2,
  delay: (error, retryCount) =>
    isTransient(error) ? timer(backoff(retryCount)) : throwError(() => error),
}),

At most three attempts. A 4xx is rethrown at once.

409 is success; the catch is inside

apps/web/src/app/features/course/enrollment-controller.ts · excerpt
tap(() => this.succeed()),
catchError((error: unknown) => {
  // 409: already enrolled (say, from another tab). For the user, that's success.
  if (error instanceof HttpErrorResponse && error.status === 409) {
    this.succeed();
  } else {
    this.status.set('error');
    this.error.set(problemMessage(error));
  }
  return EMPTY;
}),

Inside send(), so the intents stream survives and the next click still works.

Say it plainly

Retrying a POST is only safe because of the key.

Without it, a retry after a timeout is exactly how duplicates happen.

The query lives in the URL

The trade-off

Cost

A learning curve, and two reactive models: "state or event?" is a review question.

Payoff

Each concurrency decision is one visible, testable operator.

What production would add

  • Jitter on the backoff, so clients don't retry in lockstep
  • Respect Retry-After on a 429
  • Server-side timeouts: client cancellation doesn't stop server work

Traps

  • switchMap on a write: it cancels your interest, not the request
  • catchError on the outer stream: the feature dies silently
  • A new key per attempt, e.g. from an interceptor (retries pass through it)
  • Debouncing a submit: every legitimate click waits
  • Disabling the button instead of absorbing duplicates
  • Retrying 4xx errors
  • Two streams writing the same state with no guard
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

A user types "sig", pauses, types "nals", and the first response arrives last. Walk through it.

Answer out loud.

Model answer
  • "sig" passes debounce and distinct; switchMap requests it
  • "nals" restarts the debounce; "signals" passes
  • switchMap unsubscribes: the "sig" request is aborted
  • The late answer has no listener, so it can't overwrite
  • Proved with fake timers + HttpTestingController
Question 2 of 5

switchMap or exhaustMap for a Save button?

Answer out loud.

Model answer
  • exhaustMap: ignore clicks while the save is in flight
  • switchMap cancels only the client's interest; both saves can commit
  • concatMap when each click is different data, in order
  • Enroll: exhaustMap, busy not disabled
Question 3 of 5

Why is an Idempotency-Key needed if the button already uses exhaustMap?

Answer out loud.

Model answer
  • exhaustMap sees one stream in one tab
  • Not: a lost response + retry, a second tab, a reload, a proxy
  • Only the server can recognize a repeat
  • Same key replays; same key, other body: 422
Question 4 of 5

What happens when an error reaches the outer stream?

Answer out loud.

Model answer
  • An error is terminal: the pipeline is torn down
  • Later keystrokes go nowhere, silently
  • Catch inside switchMap; fail() → state + EMPTY
  • A spec: after a 503, the next search loads
Question 5 of 5

One idempotency key per intent, or one per attempt?

Answer out loud.

Model answer
  • Per intent; per attempt recreates the duplicate
  • Created in send(), once per accepted click
  • retry() resubscribes, so retries reuse it
  • New click after a failure: new key
  • Beware interceptors that stamp a fresh key
