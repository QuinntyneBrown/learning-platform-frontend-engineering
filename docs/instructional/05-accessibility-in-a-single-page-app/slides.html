Accessibility in a
Single-Page App

Put back what the page load used to do, announce without shouting, and let native elements do the rest.

The questions this lesson answers

  • "Nothing happens" after clicking a link: what's wrong?
  • How do you announce "12 courses found" without announcing every keystroke?
  • What's missing from a custom dropdown built from divs?
  • Which WCAG 2.2 criteria does a sticky header break?
  • How do you make accessibility part of a team's definition of done?
The thesis

A single-page app takes over the browser's jobs, so it inherits the browser's accessibility duties.

Where the app replaces a page load, it moves focus and announces. Everywhere else, native elements do the work.

Two ways to tell a screen reader

Move focus

For a new page, or when the focused element disappears. The reader reads what gets focus.

A live region

For a result or a status. The reader reads the new text; focus stays where it is.

polite: waits until the reader finishes speaking

assertive: interrupts. Keep it for errors.

One polite region for the whole app

apps/web/src/app/design-system/live-announcer.ts · excerpt
/**
 * One app-wide polite live region, for changes a screen reader user would otherwise miss:
 * a route change in a single-page app, or a button that has been replaced by its result.
 */
export class LiveAnnouncer {
  // …
  private createRegion(): HTMLElement {
    const region = this.document.createElement('div');
    region.className = 'cw-visually-hidden';
    region.setAttribute('aria-live', 'polite');
    region.setAttribute('aria-atomic', 'true');
    this.document.body.appendChild(region);
    return region;
  }

Clear, then set on a later task

apps/web/src/app/design-system/live-announcer.ts · excerpt
announce(message: string): void {
  const region = (this.region ??= this.createRegion());
  // Clear, then set on a later task: screen readers announce changes to a region, so this
  // also re-announces a message identical to the previous one. The region must already be in
  // the DOM when its text changes, which is why the first call creates it before setting text.
  region.textContent = '';
  clearTimeout(this.pending);
  this.pending = setTimeout(() => (region.textContent = message), 100);
}

Why the link moves focus itself

apps/web/src/app/shell/shell.ts · excerpt
// A plain href="#main" would resolve against <base href="/"> and navigate to "/#main",
// so the link moves focus itself. It keeps the href so it's still a real link.
protected skipToMain(event: Event): void {
  event.preventDefault();
  this.main().nativeElement.focus();
}

href="#main" alone

From /catalog, navigates to /#main: a route change.

href + handler

Still a real link. Focus lands on main, and the route stays.

No ARIA is better than bad ARIA.

Review: a dropdown built from divs

First comment: why isn't this a native <select>? If there's a real reason:

  • A name, from a label
  • Roles: combobox (or button), listbox, option
  • State: aria-expanded, and the selected option
  • Keys: Tab, arrows, Enter, Escape, Home, End, type to jump
  • Focus returns to the control when the list closes
  • A visible focus ring, and a target big enough to tap

axe on real pages

apps/web/e2e/support.ts · excerpt
/** Fails on serious or critical WCAG 2.2 AA violations; minor ones don't block. */
export async function expectNoSeriousA11yViolations(page: Page): Promise<void> {
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();
  const blocking = results.violations
    .filter((v) => v.impact === 'serious' || v.impact === 'critical')
    .map((v) => `${v.id}: ${v.help} (${v.nodes.map((n) => n.target.join(' ')).join(', ')})`);
  expect(blocking).toEqual([]);
}

What automation can't tell you

Automated checks

  • Missing names and labels
  • Invalid ARIA, bad contrast
  • Perhaps a third of real issues

People

  • Did focus go somewhere sensible?
  • Does the announcement make sense?
  • NVDA · VoiceOver · TalkBack

Accessibility in the definition of done

1Design annotates headings, focus order, names
2PR template: a keyboard pass
3Lint and axe block the build (done here)
4Screen-reader pass on key journeys
5Bugs triaged by severity
6A champion per team, and training

Production would add: Storybook accessibility tests per component · forced-colors styles · a VPAT for enterprise buyers.

Traps

  • Moving focus on query-only changes: the search box loses focus
  • Creating a live region at the moment you set its text
  • Announcing every keystroke, or every progress tick
  • role="alert" on every field error
  • Disabling a button while it works
  • A div with a click handler as a button or select
  • Removing focus outlines globally: use :focus-visible
  • Treating a clean axe run as proof
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

A screen-reader user says nothing happens after clicking a link. What's wrong, and how do you fix it?

Answer out loud.

Model answer
  • No page load: focus stayed on a vanished link; nothing announced
  • On a path change, after render: focus the h1 (tabindex -1)
  • Announce the page title in a polite live region
  • Skip query-only changes and the initial load
  • Coursewright: route-focus.ts, and a Playwright assertion
Question 2 of 5

How do you announce "12 courses found" without announcing every keystroke?

Answer out loud.

Model answer
  • role="status", always in the DOM
  • Change its text only when results settle
  • Debounce the search; short message, a count
  • Polite, never assertive
  • Long work: announce states, not percentages
Question 3 of 5

Review a custom dropdown built from divs. What's missing?

Answer out loud.

Model answer
  • Why not a native select?
  • Name, roles (combobox, listbox, option), expanded and selected state
  • Keys: Tab, arrows, Enter, Escape, Home, End, typeahead
  • Focus returns on close; visible ring; target size
  • A tested headless library; lint flags the click-only div
Question 4 of 5

Which WCAG 2.2 criteria does a sticky header most often break?

Answer out loud.

Model answer
  • Focus Not Obscured (AA): fix with scroll-padding-top
  • Reflow: at 400% zoom, let the header scroll away
  • Target Size: 24 × 24 CSS px, or spacing
  • Check with a keyboard at high zoom, not only axe
Question 5 of 5

How would you make accessibility part of the definition of done for a whole team?

Answer out loud.

Model answer
  • Accessible primitives in the design system
  • Template lint and axe, blocking in CI
  • Keyboard pass per PR; screen-reader pass per release
  • Design annotations; bugs triaged by severity
  • A champion per team, with training
