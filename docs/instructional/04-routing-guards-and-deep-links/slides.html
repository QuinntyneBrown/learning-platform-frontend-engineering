The thesis

Every URL is an entry point.

It has to survive a reload, a sign-in, and a hostile link.

The auth guard

apps/web/src/app/core/auth/guards.ts · excerpt
/** Signed-out users go to the login page, which sends them back here afterwards. */
export const authGuard: CanMatchFn = () => {
  if (inject(AuthStore).isAuthenticated()) {
    return true;
  }
  const router = inject(Router);
  const returnUrl = router.currentNavigation()?.extractedUrl.toString() ?? '/';
  return router.createUrlTree(['/login'], { queryParams: { returnUrl } });
};

isAuthenticated() is a signal (lesson 02), read once per navigation.

Signed out: a URL tree, not a navigation

currentNavigation is a signal in Angular 22 (older: getCurrentNavigation()). As of September 2026; check your version.

Return a UrlTree; don't navigate

Sketch · not in this repo · the pattern to avoid
export const authGuard: CanMatchFn = () => {
  if (inject(AuthStore).isAuthenticated()) return true;
  void inject(Router).navigate(['/login']);   // a second navigation, racing the first

};

navigate + false

Two navigations. The outcome depends on timing.

return a UrlTree

The router cancels this navigation and runs the redirect itself.

The role guard: fall through, don't leak

apps/web/src/app/core/auth/guards.ts · excerpt
/**
 * canMatch, not canActivate: when it fails, the router falls through to the `**` route, so
 * a learner sees "Page not found" and the page's existence doesn't leak. The BFF does the
 * same with cross-tenant resources (404, not 403). The BFF still enforces the role itself.
 */
export function roleGuard(role: Role): CanMatchFn {
  return () => inject(AuthStore).hasRole(role);
}
The line that matters most

The BFF still enforces the role itself.

Guards are user experience. Authorization happens on the server: lesson 08.

Two details worth knowing

Name collisions

Route data wins over path params, which win over query params.

It's user input

Any query parameter can set a same-named input. returnUrl is the example.

An absent parameter sets its input to undefined (the default behaviour).

Every page has a title

/** Each route's `title` becomes "<title> · Coursewright", the first thing a screen reader reads. */
@Injectable({ providedIn: 'root' })
export class PageTitleStrategy extends TitleStrategy {
  private readonly title = inject(Title);

  override updateTitle(snapshot: RouterStateSnapshot): void {
    const page = this.buildTitle(snapshot);
    this.title.setTitle(page ? `${page} · Coursewright` : 'Coursewright');
  }
}

1 · The host's fallback rule

No fallback

GET /courses/c1 → 404

Works until someone presses reload.

Fallback to index.html

GET /courses/c1 → index.html

The router takes it from there.

The Angular dev server does this for you. In production: a host or CDN rewrite rule (not in this repo).

safeReturnUrl

apps/web/src/app/features/login/return-url.ts
const DEFAULT_URL = '/catalog';

/**
 * Only a path inside this app. Without the check, a crafted link such as
 * `/login?returnUrl=https://evil.example` would turn a real sign-in into a phishing redirect.
 * `//evil.example` and `/\evil.example` are protocol-relative URLs to another host, too.
 */
export function safeReturnUrl(url: string | null | undefined): string {
  if (!url || !url.startsWith('/') || url.startsWith('//') || url.startsWith('/\\')) {
    return DEFAULT_URL;
  }
  return url;
}

The phishing redirect

1A crafted link: /login?returnUrl=//evil.example
2The real domain, a real sign-in page, a real password
3Redirected to a lookalike: "Session expired, please sign in again"

ConfirmDialog is hypothetical: an accessible dialog whose ask() returns Observable<boolean>.

What each mechanism covers

CanDeactivate

  • Router navigations away
  • The Back button
  • Your own accessible dialog

beforeunload

  • Reload, close the tab, a typed address
  • Only the browser's generic prompt

Autosaved drafts make the question rare.

Trade-offs, and what production would add

  • A startup round trip, for a guard that's never wrong about the session
  • Guards are UX; the server stays the authority
  • CanDeactivate guards for dirty forms
  • A preloading strategy tuned by analytics; route-level error boundaries
  • The host's fallback rule for deep links

Traps

  • canActivate where you wanted a fall-through
  • A guard that navigates and returns false
  • A guard treated as authorization
  • An unvalidated returnUrl
  • The session restored after the first navigation
  • No fallback rule on the host
  • An expensive canMatch: it runs on every navigation
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

canMatch, canActivate or a resolver: when does each run, and what does each cost?

Answer out loud.

Model answer
  • canMatch: during matching; false tries the next route
  • roleGuard: a learner gets "Page not found", no leak
  • canActivate: after matching; false cancels
  • Resolver: the navigation waits for data
  • Coursewright: canMatch, and a resource in the page
Question 2 of 5

Where would you put a "you have unsaved changes" check?

Answer out loud.

Model answer
  • A CanDeactivate guard; the page exposes its dirty state
  • Covers router navigations, including Back
  • beforeunload for reload, close and typed URLs
  • An accessible dialog; autosave drafts
Question 3 of 5

How do you keep deep links working behind authentication?

Answer out loud.

Model answer
  • The host serves index.html for any app path
  • An app initializer restores the session first
  • The guard's UrlTree carries the full returnUrl
  • Validated, then navigated to after sign-in; an E2E test proves it
Question 4 of 5

How does lazy loading interact with preloading, and when would you preload?

Answer out loud.

Model answer
  • Lazy chunks, no preloading: download on first visit
  • PreloadAllModules, or a custom strategy for flagged routes
  • Preload the next likely page, after interactivity
  • The preloader ignores canMatch: bandwidth, not security
Question 5 of 5

Why must returnUrl be validated, and what's wrong with //evil.example?

Answer out loud.

Model answer
  • User input on a trusted page: a phishing redirect
  • // is protocol-relative; /\ is the same trick
  • Accept single-slash paths only; default to /catalog
  • The router stays in-app, but return URLs reach location and servers
